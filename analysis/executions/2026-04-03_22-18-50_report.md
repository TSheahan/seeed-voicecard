# Execution Report — 2026-04-03 22:18:50

*First instrumented crash capture. Confirms sleeping-in-atomic hypothesis with full kernel BUG traces.*

**Verdict:** Root cause confirmed. Three `BUG: scheduling while atomic` events leading to kernel Oops and panic. Both TRIGGER_START and TRIGGER_STOP fire I2C writes under `snd_pcm_stream_lock_irq`, exactly as predicted by static analysis.

## Timeline

### Phase 1 — Startup device probes (t=295.8–296.7)

```
[295.835] ac108_aif_shutdown ENTER stream=Capture
[295.836] ac108_aif_shutdown EXIT stream=Capture
[295.836] seeed_voice_card_shutdown ENTER stream=Capture
[295.836] seeed_voice_card_shutdown EXIT stream=Capture
  (repeated 2 more times at t=296.689 and t=296.697)
```

Three rapid open→shutdown→close cycles with **no TRIGGER_START or TRIGGER_STOP**. These are PortAudio's device enumeration probes during `Pa_Initialize` — it opens and closes the PCM device to query capabilities without starting a stream. All callbacks run in process context, no bugs triggered.

**Timing:** Each `ac108_aif_shutdown` takes ~0.6ms (I2C writes to MOD_CLK_EN and MOD_RST_CTRL). The `seeed_voice_card_shutdown` takes <0.01ms (no I2C, just channel count restoration and `clk_disable_unprepare`).

### Phase 2 — Stream start: Bug 3 fires (t=299.351)

**Application context:** At 22:18:57 the recorder child's pipecat pipeline started. At 22:18:58 the master reported "recorder child READY" and entered wake_listen state. The PortAudio stream was opened and started to begin continuous capture.

```
[299.351500] bcm2835-i2s fe203000.i2s: I2S SYNC error!
[299.351979] TRIG_START stream=Capture cmd=1 irqs_disabled=1 in_atomic=1
[299.351999] ac108_set_clock ENTER y_start_n_stop=1 irqs_disabled=1 in_atomic=1 sysclk_en=0
[299.352017] BUG: scheduling while atomic: python/1280/0x00000002
```

**What happened:**

1. `snd_pcm_action_lock_irq` acquired `snd_pcm_stream_lock_irq` (spin_lock_irq → disables local IRQs, increments preempt_count to 2)
2. Dispatched to `seeed_voice_card_trigger` → TRIGGER_START
3. `ac108_set_clock(1, ...)` called to enable the codec clock
4. `ac108_set_clock` called `ac101_trigger(START)` (because `i2c101` is non-NULL and `_MASTER_MULTI_CODEC == _MASTER_AC101`)
5. Inside `ac101_trigger(START)`: `ac101_update_bits` → `regmap_update_bits` → `_regmap_write` → `regmap_i2c_write` → `bcm2835_i2c_xfer` → `wait_for_completion_timeout` → **`schedule()`**
6. Kernel detects `schedule()` called with preempt_count=2 → prints BUG

**Call trace (abbreviated):**

```
__schedule_bug ← schedule ← schedule_timeout ← wait_for_completion_timeout
  ← bcm2835_i2c_xfer [i2c_bcm2835]
  ← __i2c_transfer ← i2c_transfer ← i2c_transfer_buffer_flags
  ← regmap_i2c_write [regmap_i2c]
  ← _regmap_raw_write_impl ← _regmap_bus_raw_write ← _regmap_write
  ← _regmap_update_bits ← regmap_update_bits_base
  ← ac108_set_clock+0x23c [snd_soc_ac108]
  ← seeed_voice_card_trigger+0x140 [snd_soc_seeed_voicecard]
  ← snd_pcm_do_start [snd_pcm]
  ← snd_pcm_action_lock_irq [snd_pcm]
  ← snd_pcm_common_ioctl [snd_pcm]   (SNDRV_PCM_IOCTL_START)
```

**Outcome:** The I2C transfer completed successfully — another CPU core serviced the BCM2835 I2C IRQ while core 0 had local IRQs disabled. `ac108_set_clock EXIT y_start_n_stop=1 ret=0 sysclk_en=1` at t=299.353464. The function returned normally, but the kernel scheduler's per-CPU runqueue state is now corrupted.

**Note:** The offset `+0x23c` in `ac108_set_clock` corresponds to the `ac101_trigger` call path, not the later `ac108_multi_update_bits` calls. This means the first I2C write to trigger the BUG is from the AC101 codec's start path, before the AC108's own PLL/I2S clock writes.

### Phase 3 — Cascading scheduler corruption (t=299.353)

```
[299.353561] BUG: scheduling while atomic: python/1280/0x00000000
```

Immediately after `ac108_set_clock` returns, a **second BUG fires** — but with preempt_count=0x00000000. This is not from driver code; the call trace shows:

```
__schedule_bug ← schedule ← schedule_hrtimeout_range_clock
  ← schedule_hrtimeout_range ← do_sys_poll ← __arm64_sys_ppoll
```

The python process attempted a `ppoll()` syscall (normal operation — event loop polling). The scheduler detected corrupted internal state even though the preempt_count appears clean. This is the cascading effect: the first `schedule()` under spinlock corrupted runqueue metadata, and subsequent scheduling operations trip over it.

**Taint flag progression:** `C O` → `WC O` (WARN added after first BUG).

### Phase 5 — Stream stop: Bug 1 fires (t=336.217)

**Application context:** At 22:19:34.770, Ctrl+C triggered SIGINT. The recorder child initiated safe shutdown, signaled paComplete to the PortAudio callback. PortAudio's internal thread called `snd_pcm_drop` to stop the capture stream.

```
[336.217075] TRIG_STOP stream=Capture cmd=0 in_irq=0 irqs_disabled=1 in_atomic=1 path=synchronous
[336.217101] ac108_set_clock ENTER y_start_n_stop=0 irqs_disabled=1 in_atomic=1 sysclk_en=1
[336.217123] BUG: scheduling while atomic: python/1280/0x00000002
```

**What happened:**

1. PortAudio called `snd_pcm_drop()` via ioctl (not from IRQ — `in_irq=0`)
2. `snd_pcm_drop` acquired `snd_pcm_stream_lock_irq` (preempt_count → 2)
3. Dispatched TRIGGER_STOP to `seeed_voice_card_trigger`
4. `in_irq() || in_nmi() || in_serving_softirq()` = false → **synchronous path taken**
5. `ac108_set_clock(0, ...)` called directly under the stream lock
6. `ac108_multi_update_bits(I2S_CTRL, ...)` → I2C write → `schedule()` → BUG

**Call trace (abbreviated):**

```
__schedule_bug ← schedule ← schedule_timeout ← wait_for_completion_timeout
  ← bcm2835_i2c_xfer [i2c_bcm2835]
  ← regmap_i2c_write [regmap_i2c]
  ← _regmap_update_bits ← regmap_update_bits_base
  ← ac108_multi_update_bits+0x7c [snd_soc_ac108]
  ← ac108_set_clock+0x124 [snd_soc_ac108]
  ← seeed_voice_card_trigger+0x264 [snd_soc_seeed_voicecard]
  ← snd_pcm_do_stop [snd_pcm]
  ← snd_pcm_drop [snd_pcm]
  ← snd_pcm_common_ioctl [snd_pcm]   (SNDRV_PCM_IOCTL_DROP)
```

**Key difference from TRIGGER_START:** The offset `+0x124` in `ac108_set_clock` corresponds to the `ac108_multi_update_bits(I2S_CTRL, ...)` call in the stop path (disabling TXEN/GEN bits). This is a direct AC108 register write, not via AC101.

The I2C transfer again completed: `ac108_set_clock EXIT y_start_n_stop=0 ret=0 sysclk_en=0` at t=336.218513.

### Phase 6 — Kernel Oops and panic (t=336.218)

**Immediately** after `ac108_set_clock` returned (within 61μs):

```
[336.218574] Unable to handle kernel paging request at virtual address 0000007f948876e8
[336.218582]   EC = 0x20: IABT (lower EL), IL = 32 bits
[336.218591] user pgtable: 4k pages, 39-bit VAs
[336.218607] Internal error: Oops: 000000008200000b [#1] PREEMPT SMP
```

**Crash analysis:**

- **Virtual address** `0000007f948876e8` is in the userspace range (below the kernel's `0xffff...` addresses)
- **EC = 0x20: IABT (lower EL)** = Instruction Abort at lower exception level — the CPU attempted to **execute** a userspace address from kernel context
- **FSC = 0x0b: level 3 access flag fault** — page table walk succeeded but the access flag wasn't set (page not marked executable in kernel context)
- **PC = 0x7f948876e8, LR = 0x7f96d0f604** — both userspace addresses. The kernel's saved register state has been replaced with a userspace thread's register state

**Root cause of the Oops:** The three `schedule()` calls under spinlock (two from the driver, one cascading from `ppoll`) corrupted the scheduler's context-switch metadata. When the kernel attempted to return from the `snd_pcm_drop` ioctl path, it loaded corrupted saved registers (from the wrong task's stack frame or from a corrupted `thread_struct`), and the PC pointed to a userspace address.

```
[336.482452] pstore: backend (ramoops) writing error (-28)
[336.488001] Kernel panic - not syncing: Aiee, killing interrupt handler!
```

pstore write failed (error -28 = ENOSPC — ramoops region full or not configured large enough). The panic message "killing interrupt handler" is a generic panic path when an Oops occurs in interrupt-like context (the stream lock creates an interrupt-disabled environment).

## Uncertainty resolutions

### U1 — Does PortAudio drain after paComplete?

**Answer: Yes.**

Evidence: Only **one** TRIGGER_STOP event in the entire session (t=336.217). The call trace shows it originated from `snd_pcm_drop` via `snd_pcm_common_ioctl` — this is PortAudio's explicit drain, not the kernel's FD-close cleanup. If PortAudio were NOT draining, we would see a second TRIGGER_STOP from `snd_pcm_release` during `os._exit(0)` → `close(fd)`, but that never occurred (the kernel panicked before reaching FD close, but the single TRIGGER_STOP from ioctl confirms PortAudio initiated the stop).

**Impact:** The crash path is: paComplete → PortAudio drain → `snd_pcm_drop` ioctl → TRIGGER_STOP under stream lock → I2C → BUG. The FD-close path is not reached.

### U2 — Direct reboot or cascading corruption?

**Answer: Cascading corruption over 37 seconds.**

Evidence:
1. First BUG at TRIGGER_START (t=299.352) — survived, function completed normally
2. Second BUG from `ppoll` (t=299.354) — cascading, scheduler internals already corrupted
3. Third BUG at TRIGGER_STOP (t=336.217) — survived, function completed normally
4. Oops at t=336.219 — kernel jumped to userspace address, corrupted register state
5. Panic at t=336.488

**Impact:** A partial fix (eliminating only TRIGGER_STOP sleeping-in-atomic) would NOT be sufficient. The TRIGGER_START BUG fires first and already corrupts the scheduler. Both paths must be fixed. This elevates F3+F4 to equal priority with F1+F2.

### U5 — I2C IRQ affinity (partially resolved by inference)

The I2C transfers completed successfully despite local IRQs being disabled on CPU 0 (where PID 1280 ran). This proves the BCM2835 I2C IRQ was serviced by another core (Pi 4 has 4 cores). The transfer completion is visible in:
- `ac108_set_clock EXIT ret=0` (both times)
- The ~1ms gap between `ac108_set_clock ENTER` and `EXIT` (consistent with I2C transfer time, not timeout)

If the I2C IRQ were pinned to core 0, the transfer would have timed out (~1s) rather than completing in ~1ms. **The I2C IRQ is either not pinned to core 0, or is configured for multi-core delivery.** Explicit `/proc/irq/*/smp_affinity_list` check still recommended for completeness.

## Fix priority revision

The original fix ordering prioritized F1+F2 (TRIGGER_STOP) as critical and F3+F4 (TRIGGER_START) as important-but-secondary. The runtime evidence reverses this assessment:

| Priority | Fix | Rationale |
|---|---|---|
| **Critical** | F1 + F2 | TRIGGER_STOP sleeping-in-atomic is the immediate trigger for the fatal Oops. Must be fixed. |
| **Critical** (elevated) | F3 + F4 | TRIGGER_START sleeping-in-atomic fires **first** (on every stream open) and corrupts scheduler state. Even with F1+F2 applied, the TRIGGER_START corruption alone may cause crashes over longer sessions. |
| Important | F5 | Error handling in `ac108_multi_write` — does not cause crash but masks failures. |
| Important | F6 | AC101 `trigger(START)` I2C under spinlock — confirmed to fire (the +0x23c offset in the first BUG trace points to the `ac101_trigger` call inside `ac108_set_clock`). |

**Recommendation:** Apply F1–F4 as a single batch. Test. F5+F6 follow.

## Observations not in the static analysis

1. **I2S SYNC error precedes TRIGGER_START:** `bcm2835-i2s fe203000.i2s: I2S SYNC error!` at t=299.351500, 0.5ms before TRIGGER_START. This is the BCM2835 I2S controller detecting a clock synchronization issue on stream start — likely benign (happens when the I2S bit clock starts before the codec PLL locks), but worth noting.

2. **`ac101_trigger(START)` fires the first I2C write:** The +0x23c offset in the BUG trace corresponds to the `ac101_trigger(substream, cmd, dai)` call at `ac108.c:1003–1005`, inside `ac108_set_clock`. This means the AC101 codec's start path (`ac101.c:1271–1282`) is the first sleeping operation in the trigger, before AC108's own `ac10x_update_bits` and `ac108_multi_update_bits` calls. This was identified as a bonus finding in U3 and is confirmed here.

3. **pstore write failed:** `pstore: backend (ramoops) writing error (-28)` — ENOSPC. The ramoops region is either not configured or too small. This means pstore cannot be relied on for crash log recovery; serial console was the correct choice for capture.

4. **Three startup probes:** PortAudio performs three separate open→shutdown→close cycles during initialization, without starting a stream. These are harmless but show that `ac108_aif_shutdown` runs 3 times before the first TRIGGER_START.
